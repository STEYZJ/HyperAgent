## Step 1 - DeepSeek API 能力增强准备
- 上一步：框架已经具备 LLM provider 配置、对话保存、agent-chat/agent-plan/agent-act 等基础能力，但 LLM 请求层只支持 model、temperature、max_tokens。
- 这一步：根据 DeepSeek API 文档需求，准备扩展统一 LLM schema、请求构造器、CLI 参数和 agent loop 参数透传。
- 为什么这么干：模型选择、思考模式强度、JSON 输出、工具调用等能力应该进入统一 LLM runtime，而不是散落在具体 agent 或训练模块里，这样才能兼容多厂商并保持解耦。
- 执行内容：创建任务分支 task-deepseek-api-options，检查当前 LLM runtime、CLI 和 schema 的实现边界。
- 效果：确认 DeepSeek 当前仍使用 openai_compatible 最小请求路径，具备低风险扩展点。
- 下一步：实现 DeepSeek/OpenAI-compatible 可选参数，包括 thinking、reasoning_effort、response_format、top_p、extra_body_json，并补充测试和 dry-run 示例。

## Step 2 - 实现 DeepSeek LLM 参数通道
- 上一步：已经确认 LLM runtime 的扩展点在 schema、request builder、CLI 和 agent loop 参数透传。
- 这一步：扩展 LLM schema 与 OpenAI-compatible 请求构造器，并给 llm-dry-run、llm-send、agent-chat、agent-plan、agent-act 增加模型能力参数。
- 为什么这么干：DeepSeek 的思考模式、reasoning_effort、JSON 输出和工具调用都属于 LLM runtime 能力；统一放在 runtime 可以避免 agent、训练、评估模块直接依赖具体厂商。
- 执行内容：新增 LLMMessage 的 tool_call/reasoning 字段，新增 LLMResponse 的 reasoning_content/tool_calls/usage/message 字段；LLMRequestBuilder 支持 thinking、reasoning_effort、response_format、top_p、user、extra_body；CLI 增加 --thinking、--reasoning-effort、--json-output、--extra-body-json、--top-p、--user-id。
- 效果：DeepSeek v4-flash/v4-pro 可以通过 --model 选择；思考模式开启时按文档避免采样参数进入请求；工具调用等未封装字段可通过 extra-body-json 透传。
- 下一步：补充单元测试、更新 README，并运行语法检查和测试套件验证不破坏原有 agent workflow。
